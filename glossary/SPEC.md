# 用語集の仕様

「技術用語ガイド」は、解説動画やセミナーを聞きながら技術(AI駆動開発など)を学ぼうとしている**初心者(非エンジニアを含む)**のために、
音声認識の文字起こしから技術用語を拾い、ひとこと解説をリアルタイム表示するツール。
このファイルは、その用語集データ(`glossary/parts/*.json`)の書き方を定める。

## ファイル形式

JSON配列。1用語を1行で書く(差分を読みやすくするため)。

```json
[
 {"id": "web_cookie", "level": 1, "display": "Cookie", "aliases": ["Cookie", "クッキー"], "sense": "Webサイトがブラウザに保存させる小さなデータ", "short": "Webサイトが、あなたのブラウザに保存しておく小さなメモ。ログイン状態の維持などに使われる。", "other": "お菓子のクッキー"},
 {"id": "web_dns", "level": 2, "display": "DNS", "aliases": ["DNS", "ネームサーバー"], "sense": "ドメイン名をIPアドレスに変換する仕組み", "short": "「example.com」のような名前を、コンピューター用の住所(IPアドレス)に変換する、インターネットの電話帳。"}
]
```

## フィールド

| フィールド | 必須 | 内容 |
|---|---|---|
| `id` | ○ | 半角英小文字・数字・アンダースコア。**ファイルごとに指定された接頭辞**を付ける(例: `web_`)。全体で一意。 |
| `level` | ○ | 1=初級 / 2=中級 / 3=上級(下記)。 |
| `display` | ○ | カードの見出しに出す正式な表記。 |
| `aliases` | ○ | 文字起こしの中で一致させる表記の配列(下記のルール厳守)。 |
| `sense` | ○ | その用語の技術的な意味を表す**短い名詞句**(40字以内目安)。AIモデルに「この意味で使われているか」を判別させる選択肢として使う。 |
| `short` | ○ | 初心者向けのひとこと解説。**1〜2文、90字以内**。 |
| `other` | △ | その語に**日常語としての別の意味**がある場合だけ書く(例: コミット→「約束する・全力で取り組むという一般的な意味」)。ない場合はフィールドごと省略。 |

## レベルの基準

- **1 初級**: 非エンジニアがAI駆動開発を始めて最初の1〜2ヶ月で出会う基本語。PC・Web・AIの基礎。(例: ファイル、拡張子、ブラウザ、サーバー、API、プロンプト、GitHub、デプロイ、ChatGPT)
- **2 中級**: 自分でアプリを作って公開し始めた人が出会う語。(例: データベース、認証、環境変数、CI/CD、RAG、MCP、Docker、リファクタリング)
- **3 上級**: エンジニア実務の設計・運用・セキュリティ、AIの仕組みに踏み込んだ語。(例: マイクロサービス、オブザーバビリティ、量子化、RLHF、ゼロトラスト、冪等性)

迷ったら低いほう(やさしいほう)に倒す。

## `short`(解説)の書き方

- 読者は非エンジニアかもしれない。**専門用語を別の専門用語で説明しない**。どうしても使うなら、用語集にありそうな基本語だけ。
- 「何であるか」+「何の役に立つか/どんな時に出てくるか」を、聞きながら3秒で読める長さで。
- たとえ話は有効(例: DNS=インターネットの電話帳)。ただし不正確になるたとえは避ける。
- です・ます調ではなく、体言止めや「〜のこと。」「〜する仕組み。」の簡潔な文体。
- 事実として正確であること。製品の説明は、開発元と「何をするものか」を書く。バージョンや価格など変わりやすい情報は書かない。

## `aliases`(一致させる表記)のルール — 誤爆防止のため厳守

文字起こしの文字列に対して**部分一致**で探すので、雑な別名は誤爆の原因になる。

1. **カタカナ・漢字・ひらがなの別名は3文字以上**。2文字以下は登録しない(「型」「木」「ラグ」のような語は、`型定義` `型エラー` のように複合語で登録する)。
2. **半角英字の別名は2文字以上**。英字は単語境界つきで照合される(`PR` は `Pro` に当たらない)。4文字以上の英字は大文字小文字を区別しない。
3. **日常会話で頻出する語をそのまま別名にしない**(例: 「コード」「データ」「ページ」「テスト」「モデル」「ツール」「ファイル」単体)。初級語としてどうしても必要な場合は、必ず `other` を書く。より安全なのは複合語にすること(「ソースコード」「テストコード」)。
4. **他の一般的な語の一部になる別名を避ける**(例: 「ログ」は「ブログ」「カタログ」「ログイン」に当たる → `ログファイル` `エラーログ` `ログを確認` のようにする。「ノード」単体も避ける)。
5. 日本語の音声認識(Chrome)の出力を想定する。英語の略語はたいてい英字のまま出る(API, LLM)。製品名や英単語は**カタカナ読みでも出る**ので、カタカナ表記を別名に入れる(例: `Supabase` と `スーパーベース`、`Kubernetes` と `クバネティス` `クーバネティス`)。ありがちな表記ゆれ(長音の有無: `サーバー`/`サーバ`、`ユーザー`/`ユーザ`)も入れる。
6. 1用語あたり別名は1〜6個。`display` と同じ表記も別名に含めること(別名にないと一致しない)。

## 重複の禁止

- 既存の `glossary.json`(190語)に**すでにある用語は作らない**。作業前に必ず読んで確認すること。
- 自分の担当範囲の外の用語は作らない(他の担当者が作る)。境界があいまいな語は、担当範囲の説明に書かれたほうに従う。

## 完了条件

1. 指定されたファイルパスに、指定された語数(±10%)のJSON配列を書く。
2. `python3 glossary/validate.py <自分のファイル>` がエラーなしで通ること(通るまで直す)。
3. 最終報告は、語数・レベル別の内訳・判断に迷った点を数行で。用語の一覧を報告に貼らない。

他のファイル(`app/`, `scripts/`, `glossary.json`, 他の人の `parts/*.json`)は**編集しない**。サーバーの起動やgit操作もしない。
